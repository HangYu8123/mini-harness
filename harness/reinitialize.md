# Re-initialization — reuse existing repo_info

Read by `mh-init` when the target repo already carries generated overviews. Re-initialization never starts from scratch and never discards existing memory: **validate the existing claims → update with a targeted diff → revalidate the repo as a whole.**

## Mode detection (per overview file)
After the ensure-files step, inspect each overview's **content**, not existence (the ensure step creates empty placeholders): non-empty → **re-initialize** mode; missing or empty → **fresh**. Modes are per file; a run is a re-initialization when at least one overview is in re-initialize mode.

## Validate existing claims
Each overview-generating analyst receives the existing overview and, instead of drafting from scratch:
1. re-derives every claim against the current code — open the file(s) the claim describes; plausibility is not validation;
2. validates cross-file claims at both ends (a pipeline edge or dependency spanning two files is confirmed only when both still support it — cross-file drift is the hardest to catch);
3. uses git history to prioritize files changed since the overview was written, still spot-checking unchanged ones;
4. returns the existing overview as baseline plus a **[validation & diff report]**: confirmed · stale/incorrect (with the correction) · new files/modules missing · obsolete entries whose files are gone.

## Update with diff
Turn the report into targeted edits: preserve confirmed content and wording (including manual curation); correct stale claims; append new entries; delete obsolete ones; touch the pipeline diagram only where the diff requires it. Re-read the file immediately before writing and rewrite only the sections that changed — never blank-and-rewrite.

## Merge known issues
`the `## Auto-generated (init)` section of `known_issues.md`` is merged, never overwritten: validate each existing entry against the current code — drop resolved entries or those whose root-cause code is gone, keep those that still hold, append new findings.

## Repo-wide revalidation (after both overviews, before the issue scan)
1. The pipeline diagram matches the real entry points and control/data flow.
2. The two overviews agree — same scripts, same roles, no contradictions.
3. Every file in the file structure is accounted for; nothing described has ceased to exist.
Fix mismatches in the overviews before continuing.

**Scope.** Only the two overviews and the auto-generated section of `known_issues.md` are mode-dependent. `preference.md`, `persistent_issues.md`, `past_QA.md`, `update_logs.md`, `harness_effect.md`, and `exec_traj/` are never regenerated by an init.
